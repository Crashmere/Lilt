# Architecture

Lilt combines manually supplied music and MV libraries with browser playback. A static Go program embeds the React frontend and uses one application-owned SQLite catalog. `nas` is the authoritative application and data host; `ali` and `vps` are authenticated gateways, not independent libraries.

## MV Library and Playback

MVs have independent catalog records and do not enter song collections, playlists or listening statistics. Music and video share durable chunk transfers, authoritative offsets and complete SHA-256 verification. Upload sessions record their media kind separately; existing unqualified sessions remain audio. Video duplicate checks use current complete-file hashes, including trash, and never change an existing MV's edited metadata or restore it implicitly. Completion validates a video stream and decodes an initial frame before preserving the supplied bytes under `originals/videos/`. The MV record and completed upload receipt commit together. Retry after an interrupted transfer or publication reuses acknowledged staging or the completed receipt. Video originals are immutable; title, artist and favorite edits update only the catalog, and trash retains the original and derivatives.

The player uses a custom control surface adapted from Curio/Aura's interaction patterns without their gallery-specific frame selection or HLS runtime. It prefers range-capable native playback and switches to compatible playback if the browser rejects the container or original stream. Users can also select the playback representation explicitly. Compatibility preparation is asynchronous: the browser polls a small authenticated status resource while one bounded job produces a source/recipe-addressed H.264/AAC MP4 at up to 1920 by 1080 pixels. CUDA decode/scale and NVENC encode are preferred; unsupported decoding uses CPU decode with GPU scale/encode, and unavailable GPU processing falls back to single-threaded CPU encoding. HDR requires CPU tone mapping to SDR before encoding. The output's stream codecs, dimensions and duration are checked before publication. Originals are never replaced. Silent videos remain silent. Ready files are reusable after restart; unfinished processing restarts only on a new request.

MV position and volume are browser-local. Opening an MV restores its saved position without autoplay and pauses music while retaining the mounted audio elements and queue. Music and MV players use the same same-origin playback lease, with explicit takeover for another active tab. The modal's shortcuts own Space and five-second seeking while open; ordinary Tab remains blocked. Playback controls include ten-second jumps, speed, volume, fullscreen and conditional Picture-in-Picture. Closing the viewer stops its video without automatically resuming music. Native codec support, fullscreen and Picture-in-Picture depend on the browser. MV streams do not enter the music service worker's complete-audio cache.

MV cards and the player offer full-audio extraction into a separate song. A background job reads the entire first audio stream from the immutable original, not the compatible playback derivative or the browser's selected position. Supported audio codecs are remuxed without re-encoding; other codecs use single-threaded FLAC conversion because audio encoding has no CUDA/NVENC path. The server validates the output's audio parameters and declared stream duration, then embeds the current MV title, artist and poster using the existing metadata writer. The ordinary song-import path publishes the audio, cover derivative and catalog record and recognizes duplicate files, including historical hashes after song edits. The new song starts with independent favorites, playlist membership and listening history and does not autoplay or alter the browser queue. The MV remains unchanged. Extraction is single-source, deadline-bounded and shares the existing encode budget; metadata preparation and publication take the library write lock after extraction finishes. Completed songs survive restart, while in-memory job status and uncommitted staging do not.

## Audio Files and Library State

Audio uploads initially preserve the supplied bytes in SHA-256-addressed files. Editing a track writes its descriptive fields, version, tags, aliases, lyrics and artwork into its current audio file without re-encoding the audio stream. The catalog mirrors the edited metadata and retains the logical track ID, favorites, playlist membership and listening history. Favorites and listening activity do not rewrite audio. Tags and aliases use JSON-valued `lilt_tags` and `lilt_aliases` embedded fields; common descriptive fields use the container's tagging conventions. MP4 supplements its standard fields and artwork with iTunes freeform fields. WAV and DSF carry ID3v2.4; APE, WavPack and TTA use APEv2. Imported tags include composition credits, comments, copyright, ISRC and BPM.

One edit submits metadata and an optional replacement cover together. The server prepares output beside the current file, rereads its tags and audio parameters, and publishes only if all requested metadata and cover state roundtrip. Uploaded covers become bounded static JPEGs embedded in the audio, with one display derivative. A SQLite settings receipt owns staged files during publication; startup completes a journaled operation before opening the library and removes abandoned unjournaled edit staging. Publication updates the SHA-256, file size and catalog mapping, then removes superseded audio and playback derivatives only when no current track owns them. Explicit upload revisions remain references to their audio. Editing creates no revision and keeps no historical audio copy for the edited track. Files that cannot carry the complete selected metadata are rejected without publishing the prepared output.

Single-track, batch, import-sidecar and embedded cover processing share one server normalization path. Uploaded images are spooled to a request-scoped file and validated as JPEG, PNG, GIF or WebP. Embedded artwork is copied from its attached-picture stream without image decoding. Both sources are reduced by libvips to an orientation-correct static JPEG with a maximum 1600-pixel side, without an input-pixel ceiling. Smaller images keep their dimensions; animated inputs supply their first frame. Large inputs are not fully decoded on the Go heap. The bounded JPEG is decoded and synced before publication, and failed preparation removes its unjournaled staging. Imported display derivatives leave the supplied audio and its embedded artwork unchanged; explicit cover edits also embed the normalized JPEG in the audio.

Bulk editing uses the selected tracks; the album action selects the complete album independently of visible filters. The browser reads each track's latest metadata and timestamp, then saves its chosen fields and optional replacement cover together through one guarded write. Unchanged fields and covers are preserved; tag appends merge with the current tags. Each successful track commits separately. A failure stops the batch and retains confirmed progress in the open editor. Once any track has saved, edit choices are locked; retry handles only unfinished tracks. Closing the editor discards its retry state without undoing confirmed edits.

The catalog's `track_fingerprints` table remembers each known file's SHA-256, size and logical track ID across metadata edits. Publication records the old and new fingerprints in the same transaction as the current file mapping; the hash records do not own or retain superseded audio. Upload preparation and completion both consult current and historical hashes, so reuploading a pre-edit original returns the existing song with its edited audio and metadata unchanged. Ordinary duplicate uploads also skip supplied lyrics and cover sidecars. Active songs take precedence over trash, then current matches over historical matches. A trash match stays in trash.

Exact bytes and musical versions have different meanings. A live recording, remaster or alternate mix can remain a separate track with its own version label; matching filenames or similar audio are not duplicate criteria. Explicit replacement changes the audio attached to an existing logical track while retaining its ID, favorites, playlist references and listening history, and resets its hash-recognition lineage to the replacement audio. Its retired audio can be imported as a separate version. Previously accepted audio referenced by explicit upload replacements remains retained; replacement is not a storage purge.

Import reads local audio tags through FFprobe. Missing titles and track numbers may fall back to the filename; missing album and artist may fall back to supplied relative directory names. Album artist is distinct from track artist, so compilation albums can remain together. Browsing derives album and artist groups from catalog metadata and preserves disc/track order. Search includes descriptive fields, aliases and Chinese pinyin; no external source is consulted.

When several lyric tags coexist, import prefers valid LRC text with timestamps over plain text. Candidate order is `lyrics`, `syncedlyrics`, `unsyncedlyrics`, `unsynchronised_lyrics`, then lexically sorted `lyrics-*` language fields. Empty or invalid candidates are skipped; without timed text, the first valid plain candidate is used. Lyric writeback replaces these editable fields together so an older timed alternative cannot override a newly saved lyric. Preserved source-material tags remain separate.

Explicit leading LRC timestamps enable synchronized lyric highlighting, seeking and timing adjustment even when other content is untimed. Timestamps accept dot or colon fractional seconds; an inline timestamp alone does not create a timed row. Embedded JSON credits contain a nonempty `c` array of string `tx` fragments and may include a finite numeric `t` in milliseconds; negative times preserve pre-roll ordering, while missing or null times remain untimed. Credit fragments display as joined text; embedded links are ignored. Mixed lyrics show untimed text and credits above the timed rows in source order, without seeking or highlighting them. Timestamp-only rows remain timeline entries for instrumental gaps. Lyrics without valid line starts display their complete plain text with timing markers and metadata headers removed. Stored lyrics and audio remain unchanged by display parsing.

The music library's filter dialog combines descriptive metadata, a tag, year/tempo/duration ranges, source audio properties, favorite/cover states, lyrics types and playlist membership counts. All active conditions intersect with the current search; text fields match normalized case- and accent-insensitive keywords. Genre, version, composer, lyricist, tags, year, tempo and bit depth can also match any present value or an empty field, independently of a specific value. Selecting presence clears that field's value or bounds. Whitespace-only text and empty tag lists are empty; zero or absent numeric metadata is unknown and does not satisfy an active range. Automatically populated names and required audio properties have no empty-field selector. Lyrics choices are unrestricted, absent, TXT (plain or partially timed text) or LRC (a timed document with fully timed ordinary lyric rows). Valid JSON credits and standard LRC headers do not require timestamps for body completeness. This classification describes body timing completeness, not whether the player can use existing timestamps. The catalog derives the type before omitting lyrics bodies from list responses, so filtering requires no per-track lyrics fetch or persistent catalog update. The same type appears in the applied lyrics column. Playlist counts include distinct resolved manual and smart memberships, matching the displayed membership list; repeated entries within one playlist count once. The dialog previews counts without changing the list, applies its draft on submission and discards unapplied changes on dismissal. Each applied filter adds one column to the music library table, labeled with its field name and displaying each track's actual value, including explicit empty states and numeric playlist counts. A bounded range or presence choice remains one column; unapplied drafts add none. The table scrolls horizontally when the columns exceed its available width, and clearing filters restores the ordinary table. Filters stay in browser memory across navigation, apply only to the music library and share the same tag state as its existing tag buttons. Filtering uses the loaded catalog without server writes or queue changes.

Legacy catalog entries without composition-credit fields load those fields from their current audio when opened for detail or editing. Catalog-only favorites and trash operations preserve that pending-import state. The first audio edit saves the imported fields together with the requested changes; startup does not rewrite existing songs.

Ordinary (普通歌单), external (外部歌单) and game-soundtrack (游戏原声) playlists store ordered track IDs and share the same membership operations. External and game-soundtrack playlists are omitted from the sidebar, but remain available on the playlist page, in membership details and as add/upload destinations. Smart playlists evaluate catalog rules such as favorites, tags, artist, genre, year and listening recency. The playlist page groups the four kinds in that order, preserving the catalog's recent-update ordering within each group and omitting categories with no matching playlists, including during search. New and existing playlists use the same four-choice type selector. These kinds are stored in each playlist's JSON document and require no schema migration or rewrite of existing playlists. A playback queue is a snapshot independent of those collections: editing a playlist does not replace an already playing queue. Moving a track to trash changes catalog visibility and is reversible; it does not unlink its audio or artwork.

Track selection applies to the current filtered list. Its toolbar stays at the top of the scrolling list and provides playback, editing and playlist actions; its additional actions include favorites, select-all/invert, trash and removal from non-smart playlists. Favorite and trash batches use sequential existing track requests, stop on the first failure, refresh once and report the completed count. Trash removes every occurrence of successful IDs from the browser queue while preserving the remaining order and playback intent. Playlist removal submits only the selected IDs, preserving other membership under the server's playlist-write lock. Trash and playlist removal require confirmation.

## Durable Uploads and Playback

Each upload has a retained session and acknowledged offset in SQLite, with partial bytes under `uploads/`. The server accepts at most 32 MiB per raw chunk, flushes accepted bytes before acknowledgment and checks the complete SHA-256 before publishing an original. Resume follows the server's offset rather than a browser estimate. Canceling an incomplete upload removes only that session's partial bytes. The [API](API.md#resumable-audio-uploads) defines request and conflict behavior.

The browser player streams accepted original audio bytes, with no playback-file selector or automatic transcoding fallback. Unsupported original formats require a browser that can decode them. Audio comes from the server, with conditional browser buffering and complete-file caching described below; playback still requires authorized network access. Original downloads remain available for use outside Lilt. The API retains standard and compact requests for separate AAC/M4A derivatives at nominal 192 kbit/s and 96 kbit/s, respectively, with at most two channels and a 48 kHz sample-rate ceiling. Those outputs are reused by source fingerprint and quality. One CPU encoding operation runs at a time; FFmpeg probing and audio encoding do not require the shared NVIDIA image runtime.

Streams and original downloads support byte ranges. The response identifies the selected playback quality separately from the source audio's properties. Having a lossless original does not imply that a compatible AAC stream or the browser/device output path is lossless.

Original streams and downloads read the committed catalog without acquiring the audio/upload write lock. Opening the immutable audio file pins its bytes for that response, so tag writeback, upload completion and compatible encoding do not block ordinary playback. If publication removes the old path before it can be opened, the reader retries the catalog lookup once. Existing responses retain their opened file while new requests use the published version.

The first compatible request may wait for encoding. Uploaded files are constrained to locally decoded audio formats; media commands disable network protocols and do not execute user-selected commands. Safe static artwork is served in place of uploaded active content.

## Browser Continuity and Storage

The player remains mounted while library views, search results, dialogs and playlists update. Its queue, current track, position, repeat/shuffle preferences and volume are saved without requesting audible playback on page startup. Starting or continuing playback is an explicit user action and remains subject to browser autoplay rules.

The player uses metadata preloading on restoration and requests playback immediately on an explicit play action, without an application-imposed starting buffer or a wait for lyrics. Restoration can reuse complete cached audio but otherwise preserves the native metadata request; clicking Play does not discard that preload by changing its URL. Worker-managed streams return constructed responses consistently across network passthrough, sparse fills and cache hits, because Chrome rejects mixing native response URLs with constructed responses for one media source. The passthrough body remains streamed without another download or a complete-file wait. Fresh browser installations can finish their already open native response while the worker becomes available; subsequent managed requests use shared buffering. Waiting and seeking show a cancelable loading state; the timeline distinguishes played, buffered and unbuffered audio. Fresh streams use their GET directly. Media failures trigger a bounded diagnostic HEAD to distinguish expired authorization, missing tracks, unsupported media and transient transport failures. Temporary failures receive at most three reloads with 1/2/4-second backoff, preserving the playback position and listening session. A foreground load with no media progress for 45 seconds can also reconnect; incoming progress, background suspension and deliberate pause do not trigger that idle recovery. Five seconds of advancing playback resets the recovery budget. Pause, track changes and another tab taking over cancel pending recovery; offline requests wait for connectivity, and exhausted recovery requires an explicit play action.

When the scoped service worker is available, versioned original-stream requests share a bounded range fill with native playback. The first response streams immediately after its headers arrive, without waiting for the whole requested range. One fill request runs at a time across the current and next tracks. Sparse in-memory byte intervals also retain container indexes and distant seeks, so later filling requests only missing intervals. Transport retries retain received bytes and use validated `If-Range` requests with bounded backoff; player recovery clears the transport error, not the partial audio. Its byte length and ETag must match the selected original before a complete response is published to `lilt-audio-v1` Cache Storage, including when transport ends just after the final byte. Each file is limited to 128 MiB; retained in-memory files and the complete-file cache are bounded to 256 MiB, with at most eight complete cached files. Complete-file publication evicts older downloads and superseded versions of the same track. Unwanted partial files remain reusable within the memory budget, but worker termination loses them. Storage failures leave streaming usable, and unsupported workers or files outside the bounds retain native streaming.

The player prepares only the actual next entry in its independent queue. A standby audio element and next-track lyrics start loading when the current element has at least 20 seconds of continuous buffer ahead, or is buffered to the end. Below 12 seconds or during waiting/seeking, current-song filling takes priority without a rate cap and speculative downloading pauses. Current-song requests contain at most 2 MiB, reducing repeated round trips without requiring that much data before playback; healthy filling is paced at 1.25 times the file's average byte rate. Next-track filling uses 128 KiB requests, at most 64 KiB/s, and retains approximately 12 seconds of audio plus a metadata allowance; it can continue to the end once the current element is fully buffered. Library, cover and lyrics transfers temporarily suspend non-urgent filling. Deliberate pause stops both player-driven background fills; an open lyrics workbench has independent full-file preload demand. These thresholds avoid repeated start/stop around one boundary. Queue changes invalidate the standby, and single-track repeat has no next-track prefetch. Shuffle at the end of an all-repeat queue waits until the new order is known. A matching standby is promoted without changing its source or reloading its media, preserving downloaded and decoded data. Insufficient sustained bandwidth can still exhaust the current buffer.

`audioVersion` comes from the catalog's current original SHA-256, not the general track update timestamp. Favorites and listening history do not invalidate audio, while tag writeback and replacement do. New requests that reuse stored or in-memory audio pass a network HEAD through the authenticated gateway and check the ETag before serving bytes. Failed authorization and transport errors never fall back to cached audio. Promoting the standby continues its already authorized media response, like continuing the current song. The cache version is a browser key, not an endpoint for historical originals; the server always serves the current committed file. Existing open responses can finish their pinned version without restarting playback after metadata updates.

Keyboard shortcuts apply throughout the active Lilt page, including dialogs and focused player controls: Space toggles playback, Left/Right seek by five seconds, Up/Down change volume by five percentage points, Shift+Left/Right invoke previous/next track, and the unmodified backquote key toggles the lyrics panel. Text inputs (including search), textareas, selects, editable content, IME composition and Ctrl/Command/Alt combinations retain their normal behavior. Holding Space, a track-switch shortcut or backquote triggers only once; seeking and volume changes repeat while held. System-wide media controls use Media Session support rather than page keyboard events.

The player and library-row ellipsis buttons open one shared song-specific More Features menu. Additional song operations belong in this menu.

Each browser keeps its player snapshot locally. Library data, playlists and listening history are shared through the server; queues and playback progress remain browser-local. Same-origin tabs coordinate playback locally. Legacy server snapshots remain in the catalog, without active read/write endpoints.

Listening updates use a session identifier and cumulative actual listening time so retries do not add the same seconds again. Pending updates remain browser-local until they can be sent to the server. Browser player state is not part of NAS data recovery.

IndexedDB saves the library metadata and its ETag in one transaction. Startup displays the saved metadata before requesting the current library with that validator. A 304 response preserves the in-memory library object and performs no IndexedDB write; changed responses replace the snapshot. Library and lyrics reads use cancelable 90-second attempts and at most three retries for transient failures. This retry helper is limited to reads; resumable uploads retain their offset-reconciled retries. Refresh preserves existing content, and superseded library responses are discarded. A library authorization failure clears the displayed library and stops playback.

The server retains one serialized library response up to 8 MiB in memory. Successful track publication, favorites, trash changes, playlist writes and listening updates invalidate it. Time-sensitive smart playlists also expire the snapshot at their next possible unheard-days boundary. The complete response's content hash supplies its ETag; unchanged requests reuse the serialized response without reparsing tracks or rebuilding search text and collections. This cache introduces no database schema or persistent server-cache directory.

Display cover URLs use the cover file's modification time and size rather than the track's general update timestamp. The browser loads the current and next queued tracks' lyrics independently of audio readiness or whether the lyrics panel is open. Readers share each in-flight versioned request; obsolete requests are canceled when their last consumer leaves. The browser retains lyrics for up to 32 tracks and 2 MiB of UTF-16 text in a least-recently-used memory cache, keyed by track and lyrics content version. The panel consumes the mounted player's lyrics state rather than starting another read. Favorites and unrelated metadata changes preserve both resources; changed lyrics or display artwork get new versions.

The lyrics panel's 0.2-second timing controls immediately save the cumulative adjustment in the embedded lyrics' LRC `offset` tag through the existing metadata writeback path. Each adjustment reads the latest lyrics and uses their track timestamp to guard publication against concurrent edits. The panel displays the saved offset and applies it once to highlighting and lyric-line seeking; no browser-only timing override remains. Saving updates the loaded track without restarting playback. A failed or unconfirmed write retains the displayed lyrics and reports the error.

The [lyrics workbench](LYRICS.md) offers a separate explicit-save workflow for row/source editing, millisecond timing, linked translations and enhanced LRC word starts. Its audition override uses the same mounted audio elements while retaining the queue and suppressing audition history/state publication; exit restores paused playback. Session-local full-audio preloading shares the existing range cache, and waveform peaks are calculated in the browser within bounded file/PCM budgets. Serialization, ordered timing and candidate-version checks are recalculated on document changes rather than playback ticks. Browser drafts share the existing IndexedDB settings store. Optional server waveform/alignment jobs share SQLite settings, own disposable audio hard links under `analysis/`, and run in a separate restricted process. A candidate must be reviewed and applied to the draft before guarded lyrics/audio-version writeback; the model never publishes metadata automatically.

A scoped service worker preloads the embedded build's shell manifest with at most four simultaneous resource requests, checking each resource's validator before publishing the complete shell. Fingerprinted assets prefer the cached copy; navigation and fixed-name resources use the network first. Only transport failures fall back to the saved shell, not HTTP authorization failures. Cache cleanup retains the current and previous shells and builds still used by open tabs; clients that cannot report their assets defer cleanup. Other business APIs and original downloads remain outside the service worker's audio handling. Existing legacy audio stores are left untouched but are no longer read or written. The browser or user can remove local storage, and another device does not automatically receive browser-local state. Browser suspension can interrupt speculative loading or a partial fill; the application does not promise background completion or offline playback.

Media Session actions integrate with lock-screen and headset controls when supported. Home Screen installation changes the launch experience, not operating-system background execution guarantees. Background track changes and cross-tab coordination remain subject to browser suspension. Ordinary Tab/Shift+Tab traversal and focus-only decoration follow the user's shared keyboard policy while preserving text input, selections, carets, IME composition and modifier shortcuts.

## Access and Resource Ownership

ServerPortal protects production pages, scripts, APIs, streams and uploaded media. Lilt validates mutating browser requests against the privately configured HTTPS Origin set and the forwarded request Host. Nginx preserves the `/lilt/` prefix and full Host, including the VPS port, and inherits shared authentication/cookie-renewal headers.

Only exact GET/HEAD branding paths and the public manifest bypass authentication. The service has no separate account roles, social sharing or navigation back to Portal. `deploy/portal.json` declares the application-owned database, original objects, durable uploads, covers, playback derivatives and operational resources.

Full external backup and recovery belong to the server-operations agent. Rebuildable derivative labels in Portal do not exclude stored covers or playback files from that full scope. The current catalog check validates SQLite integrity/schema and referenced original existence and size; it is not a complete cryptographic rehash of the original tree.
